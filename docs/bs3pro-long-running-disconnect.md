# BS3 Pro 长时间运行断蓝牙调查（2026-11-12）

## 结论与证据边界

现场设备经现有 Core 的只读 IPC 确认为 BS3PRO，固件 `0.0.2.4`；安装版为 THRM 3.8.0。
安装目录的 11 月 9–11 日日志记录了真实底层断链，不只是 UI 状态变化。
目前不能断言设备确实重启：没有 MCU 复位原因或 Bluetooth HCI 断开原因。

**首次物理断链的唯一根因尚未锁定。** 以下补丁修复已经确认的软件通信缺陷，并保存下一次异常的必要证据；单元测试通过不能替代数小时实机运行。

## BS3 Pro 固件核对

本地原始镜像：`ota/CH591_For_BS3PRO_Ver0.0.2.4.bin`，172040 字节，SHA-256：

```text
a3ff0b48c760e1d6332979c056071bda6deb47896717ea217c5fb5453d544fe5
```

使用 Capstone 的 RV32 + 压缩指令模式核对，以下是该版本文件偏移，不适用于 BS2 Pro：

| 命令 | 入口/调用路径 | 核对结果 |
| --- | --- | --- |
| 分发 | `0x23FA`，回调注册 `0x2818` | BS3 Pro 采用回调表，不能沿用 BS2 Pro 分发地址 |
| 0x21 | `0x63C4` → `0x4D3E` | 实时模式有效时写 RAM 中的目标 RPM，再回复 ACK；该路径未发现直接闪存写入 |
| 0x23 | `0x66A2` → `0x658C` | 切模式并更新运行状态；不同于 BS2 Pro，状态修改还会经 `0x5376` 比较并标记配置为脏 |
| 配置保存 | `0x533A` | 周期检查脏标记，调用 `0x5320` 保存；所以不能把模式切换一概当作完全不持久化 |
| 0x44 | `0x5EF8` → `0x5BDC` → `0x5AB0` | 构造原生动画并更新渲染状态；未发现直接调用自定义灯效持久化路径 |
| 0x43 | `0x5F24` → `0x52E4` | 自定义灯效应用会进入持久化路径，应减少重复提交 |

尚无同机官方 APP 的完整连续通信抓包。因此“官方有特殊心跳/特殊连接参数”仍是假说，补丁没有凭空添加 0x23 心跳、修改配对参数或刷写设备固件。

## 已修复的软件缺陷

1. **原生 Windows 挂起写入被继续复用。** 本地 go-hid 0.15.0 的 `hid_windows.c:1127` 在 `WaitForSingleObject` 失败后直接返回，没有取消/回收 `write_ol`。后续写入可能再次使用同一 OVERLAPPED 状态及缓冲区。现在立即隔离该句柄，禁止再写，并保留报告缓冲区直到对应句柄关闭；由原有读循环退出机制关闭并恢复连接。此类故障不能用“还有 EF 上报”来放行继续复用。
2. **协议失败被直接等同断链。** 三次实时控制失败后先做只读 0x25 查询；若查询成功或最近 3 秒仍有校验有效的设备帧，保留连接并重同步实时模式。无响应时仍保留恢复能力。
3. **异步恢复跨连接生效。** 恢复任务绑定连接代次，并在实际关闭前再次检查；旧任务不能关闭新连接，已经被成功通信取消的恢复也不会执行。
4. **HID 读线程等待 Core 配置锁。** 状态回调改为尝试读取锁，锁忙时丢弃该次 UI 回调；设备层已保存数据，下一帧继续刷新。这样不会因为配置操作拖住唯一的 ACK 读取线程。
5. **定时延迟被当作唤醒。** 仅由计时间隔推测唤醒时，如果 HID 仍有新鲜有效应答，则不执行推测性断开。真实系统电源通知处理保持有效。
6. **同一自定义灯效重复上传/落盘。** 缓存已成功提交的实际灯效程序，相同程序跳过上传；断连、维护和切换到原生灯效时使缓存失效，上传失败不缓存成功状态。

## 异常记录与验证

新增固定 32 条非 EF 命令收发环形记录，以及最后一条 EF 原始状态、有效应答年龄、收发计数和连接代次。
周期状态不会挤掉最后的控制命令；断开重连会重置当前连接记录；旧读循环不能更新新连接的健康信息。
正常运行不逐帧写日志。写失败、ACK 超时、首次底层读错误、主动恢复和异常读循环退出时输出 `HID 通信诊断`，随现有应用日志进入诊断包。

回归检查包括：校验错误不能证明在线、旧连接帧不能证明新连接在线、十万次状态上报后记录仍有界且保留命令、旧恢复不能关闭新连接、挂起原生写入禁止复用、Core 锁不能阻塞状态回调、相同灯效程序不重复提交。

实机验收仍需：使用测试核心持续运行，覆盖原有智能控温和温控灯效；若再次断链，对齐第一条原生错误和诊断中的最后 TX/RX，必要时补 Bluetooth HCI 跟踪，以区分设备复位、无线链路超时与主机 I/O 故障。

## 针对智能温控灯效的追加排查与缓解

用户进一步指出怀疑智能温控灯效。统计安装版的完整日志：

| 日志文件日期 | 成功温控切灯次数 | 与前次间隔不超过 5 秒 | 不超过 10 秒 |
| --- | ---: | ---: | ---: |
| 11-09 | 1864 | 497 | 923 |
| 11-10 | 2261 | 605 | 1150 |
| 11-11 | 1256 | 424 | 724 |

这些是按日志文件归类的记录，文件会跨午夜，不等同于完整自然日统计。
8 次首次 `0x48F` 错误距最近一次成功切灯分别约为 19.6、51.9、8.6、7.9、128.9、11.2、9.1、7.9 秒。
5 次落在约 8–12 秒内，但切灯本身十分频繁；未做背景时间窗对照，也没有 HCI/复位原因，相关性不能直接解释为因果。

检查当前实现还确认了两个可避免的行为：跨入使用相同预设的另一个区间仍会发送 0x44；重放已激活的 smart_temp 配置仍会停动画、回到首段，再切到实时温度段。

追加缓解：

- 首次温度同步立即完成；后续新预设需在采样中持续至少 3 秒，实际延迟随采样间隔取整。
- 运行期温控预设写入尝试至少间隔 5 秒，包括 ACK 失败后的重试；不在设备锁里睡眠，不延迟风扇调速。
- 不同温度区间使用同一预设时，只更新区间展示，不重新发送动画命令。
- 重放已经激活的 smart_temp 配置时保留当前动画；分区配置改变才重新判定温度，使用当前传入配置而非旧缓存选择启动预设。
- ACK 失败后使预设缓存失效，避免设备已经切灯却漏回 ACK 时，主机仍误信旧预设。

3 秒/5 秒是减少命令抖动的主机策略，**不是固件要求或已证实的故障阈值**，也不保证消除所有物理断链。
新增虚拟时间回归测试覆盖 20 分钟每两秒冷热交替、稳定温度最终生效、失败重试限频、同预设区间和配置重放不重新激活动画。

建议的实机对照是维持相同风扇曲线与负载，仅把灯带设为固定单色（不要改变风扇智能控温），观察相近运行时长的断链情况，再对比新版温控灯效。
本次没有改写用户正在运行的安装版或灯效配置，以便保留原始行为作对照。
