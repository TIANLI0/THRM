# BS2PRO OTA 固件蓝牙命令分析

本文档基于 BS2PRO 固件 `CH591_For_BS2PRO_Ver0.0.3.5` 及其反汇编产物分析，目标是整理固件中可识别的蓝牙协议帧、命令分发表、常用控制命令和设备上报格式。

> [!NOTE]
> 固件镜像（`.bin` / `.hex`）与反汇编产物（`dump.S`、`fw_capstone*.asm`、`fw_pretty.asm`）为厂商版权内容，**不随本仓库分发**（见 [.gitignore](../.gitignore)）。下文引用的地址偏移基于该版本固件；本文档记录的是协议结论，THRM 的设备通信实现不依赖这些文件。

分析结论来自三类证据：

- 固件反汇编：`ota/dump.S` 中 `0x5e7a` 是 `5A A5` 协议帧入口，`0x58fe` 是命令分发表，`0x881e` / `0x8840` 是校验计算/填充逻辑。
- 现有抓包：`scripts/ble_data.md` 记录了 BLE ATT Write Command，经由 handle `0x003c` 写入 `5A A5 ...` 帧。
- 现有控制代码：`internal/device/device.go`、`internal/device/rgb.go`、`internal/types/types.go` 已实测使用多条同协议命令。

> 注意：固件命令分发表只能证明固件识别这些 `CMD` 分支；部分内部/调试命令缺少完整业务上下文，本文按置信度标注。未确认命令不建议直接对真实设备批量 fuzz。

## 传输层与 GATT

BS2PRO 的蓝牙写入层使用 BLE GATT Write Command / Write Without Response。已有抓包显示：

| 方向 | ATT | Handle | Value |
| --- | --- | --- | --- |
| 主机到设备 | Write Command `0x52` | `0x003c` | `5A A5 ...` |
| 设备到主机 | Notify | 抓包/脚本中常见 `0x0026` 或 `0000fff1-0000-1000-8000-00805f9b34fb` | `5A A5 EF ...` |

仓库脚本中曾发现通知特征 UUID 为 `0000fff1-0000-1000-8000-00805f9b34fb`。写入特征在同类设备上通常与 `FFF0/FFF1/FFF2` 私有服务族相关，但 BS2PRO 的可写特征以实际枚举结果和抓包 handle 为准。

HID 模式与 BLE payload 共用 `5A A5` 内层协议，但 HID 写入前面会额外加 Report ID `0x02` 并补齐到报告长度；BLE GATT 写入不带 Report ID。

## 帧格式

### 主机发送帧

```text
5A A5 <CMD> <LEN> <PAYLOAD...> <CHECKSUM>
```

字段含义：

| 字段 | 长度 | 说明 |
| --- | --- | --- |
| `5A A5` | 2 | 固定同步头 |
| `CMD` | 1 | 命令码 |
| `LEN` | 1 | 从 `CMD` 开始到 payload 结束的长度，即 `2 + payload_len` |
| `PAYLOAD` | `LEN - 2` | 命令参数 |
| `CHECKSUM` | 1 | `sum(CMD, LEN, PAYLOAD...) & 0xFF` |

示例：设置目标转速 1700 RPM。

```text
5A A5 21 04 A4 06 CF
```

计算：

```text
CMD=21
LEN=04
PAYLOAD=A4 06    # 0x06A4 = 1700, little endian
CHECKSUM=(21 + 04 + A4 + 06) & FF = CF
```

旧脚本中有一处把校验写成“包含 `5A A5` 再 `+1`”。两者在该协议下等价，因为 `0x5A + 0xA5 + 1 = 0x100`，低 8 位为 `0x00`。

### 设备通知帧

设备主动状态上报使用：

```text
5A A5 EF 0B <gear_settings> <work_mode> <reserved>
<current_rpm_le> <target_rpm_le> <extra...>
```

BLE 通知没有 HID Report ID。HID 读取时前面可能多一个 Report ID `0x01`。

字段解析：

| Offset(BLE) | 长度 | 字段 | 说明 |
| --- | --- | --- | --- |
| `0..1` | 2 | `5A A5` | 固定头 |
| `2` | 1 | `EF` | 状态上报命令码 |
| `3` | 1 | `0B` | 上报长度/状态类型，常见固定值 |
| `4` | 1 | `gear_settings` | 高 4 位为最高挡位，低 4 位为设置挡位 |
| `5` | 1 | `work_mode` | 常见 `0x04` 挡位模式，`0x05` 实时/自动转速模式 |
| `6` | 1 | reserved | 常见 `0x05` |
| `7..8` | 2 | current RPM | 小端 |
| `9..10` | 2 | target RPM | 小端 |
| `11..` | n | extra | 设备内部计数/状态，未完全确认 |

`gear_settings` 编码：

| 半字节 | 值 | 含义 |
| --- | --- | --- |
| 高 4 位 | `0x2` | 最高挡位标准 |
| 高 4 位 | `0x4` | 最高挡位强劲 |
| 高 4 位 | `0x6` | 最高挡位超频 |
| 低 4 位 | `0x8` | 设置挡位静音 |
| 低 4 位 | `0xA` | 设置挡位标准 |
| 低 4 位 | `0xC` | 设置挡位强劲 |
| 低 4 位 | `0xE` | 设置挡位超频 |

## 固件命令总表

以下命令码来自固件 `0x58fe` 分发表。置信度说明：

- 高：固件分支明确，且仓库代码或抓包已使用。
- 中：固件分支明确，业务语义可由分支和邻近代码推断，但缺少完整抓包验证。
- 低：固件分支明确，但看起来偏内部、调试或状态机控制，不建议直接调用。

| CMD | LEN/参数 | 功能 | 置信度 | 备注 |
| --- | --- | --- | --- | --- |
| `0x01` | 无 | 查询/返回固定设备信息块 | 中 | 构造一段固定长度回包，偏信息查询 |
| `0x02` | 无 | 查询当前配置摘要 | 中 | 回包含当前状态字节 |
| `0x03` | 无 | 初始化/启动运行态资源 | 低 | 会置内部运行标志并触发定时/状态更新 |
| `0x04` | 无 | 查询/上报系统配置快照 | 低 | 回包形态由固件固定构造，业务未完全确认 |
| `0x05` | 无 | 清除/复位某运行状态 | 低 | 写内部状态位 |
| `0x06` | 无 | 重新初始化多组运行参数 | 低 | 调用多段初始化函数 |
| `0x07` | 无 | 查询某状态字段 | 低 | 返回内部 offset `0x0C` 字段 |
| `0x08` | `gear` | 固定挡位设置 | 高 | `01` 静音，`02` 标准，`03` 强劲，`04` 超频 |
| `0x09` | 无 | 查询一个动态状态字节 | 低 | 与内部参数块相关 |
| `0x0A` | `value` | 设置一个内部开关/状态 | 低 | 返回成功/失败 |
| `0x0B` | 无 | 返回一段 18 字节左右的固定/设备信息 | 低 | 类似查询 |
| `0x0C` | `mode` | 通电自启动 | 高 | `01` 开，`02` 关 |
| `0x0D` | `mode` | 智能启停 | 高 | `00` 关，`01` 立即，`02` 延时 |
| `0x21` | `rpm_lo rpm_hi` | 实时目标转速 | 高 | 小端 RPM；建议先发 `0x23` |
| `0x22` | 不明 | 未完整实现/异常分支 | 低 | 分支很短，不建议使用 |
| `0x23` | 无 | 进入实时转速控制模式 | 高 | 常作为设置 `0x21` 前置命令 |
| `0x24` | 无 | 退出/停止实时转速控制模式 | 中 | 会清除实时模式标志 |
| `0x25` | 无 | 查询当前工作状态/挡位状态 | 中 | 返回当前模式或挡位字段 |
| `0x26` | `gear_idx rpm_lo rpm_hi` | 设置挡位档案转速 | 高 | `gear_idx` 为 `00..03`，固件会写入对应挡位转速表 |
| `0x27` | 无 | 查询挡位转速表/预设表 | 中 | 返回多组转速配置 |
| `0x41` | 无 | 灯效数据传输初始化 | 高 | 清零上传偏移并进入接收状态；无需额外 payload |
| `0x42` | data | 写入灯效数据缓冲 | 高 | 用于分块传输灯效帧数据 |
| `0x43` | 无或 `01` | 灯效提交/应用/结束阶段 | 高 | 常用于应用已上传灯效或关灯流程收尾 |
| `0x44` | `preset` | 原生灯效预设 | 高 | 固件要求 payload 恰好 1 字节；`00` 关闭，`01..05` 生成不同内置动画 |
| `0x45` | 无 | 灯效状态查询 | 高 | 只读命令：固件读取 LED 控制器状态并返回，不是上传握手 |
| `0x46` | `enable` | 灯效开关/动态灯效入口 | 高 | `00` 关，`01` 开 |
| `0x47` | `frame_idx + 10 bytes` | 写入灯效帧 | 高 | 固件不检查索引上界；缓冲区 256 字节，实际只需发到 `0x12` |
| `0x48` | `enable` | 挡位灯开关 | 高 | `00` 关，`01` 开 |
| `0xED` | 无 | 关闭内部调试/上报标志 A | 低 | 固件内部标志，非业务命令 |
| `0xEE` | 无 | 打开内部调试/上报标志 A | 低 | 固件内部标志，非业务命令 |
| `0xF0` | 无 | 触发内部配置/状态刷新 | 低 | 调用与 `0x04` 相同的配置构造路径 |
| `0xF1` | 无 | 关闭校验/调试标志 B | 低 | 影响协议校验/调试分支，不建议使用 |
| `0xF2` | 无 | 打开校验/调试标志 B | 低 | 影响协议校验/调试分支，不建议使用 |
| `0xEF` | 通知上报 | 设备状态上报 | 高 | 设备到主机方向，不是常规主机写命令 |

## 常用控制命令

### 实时转速控制

进入实时转速模式：

```text
5A A5 23 02 25
```

设置目标 RPM：

```text
5A A5 21 04 <rpm_lo> <rpm_hi> <checksum>
```

示例：

| RPM | 小端参数 | 完整 BLE Value |
| --- | --- | --- |
| 1700 | `A4 06` | `5A A5 21 04 A4 06 CF` |
| 3300 | `E4 0C` | `5A A5 21 04 E4 0C 15` |
| 3981 | `8D 0F` | `5A A5 21 04 8D 0F C1` |

退出实时转速模式：

```text
5A A5 24 02 26
```

## RGB / 灯效命令

灯效命令的校验范围同样是 `CMD/LEN/PAYLOAD`。仓库实现中的通用构造为：

```text
5A A5 <fields...> <sum(fields) & FF>
```

其中 `fields[0]` 就是 `CMD`，`fields[1]` 是 `LEN`。

### 基础灯效命令

| 功能 | BLE Value | 说明 |
| --- | --- | --- |
| 关闭 RGB | `5A A5 46 03 00 49` | `0x46 enable=0` |
| 开启/进入动态灯效 | `5A A5 46 03 01 4A` | `0x46 enable=1` |
| 查询灯效状态 | `5A A5 45 02 47` | 只读查询，不应混入灯效写入事务 |
| 温控预设 1 | `5A A5 44 03 01 48` | 绿色动画，电脑低温档 |
| 温控预设 2 | `5A A5 44 03 02 49` | 黄色动画，电脑中温档 |
| 温控预设 3 | `5A A5 44 03 03 4A` | 红色动画，电脑高温档 |
| 应用/提交 | `5A A5 43 03 01 47` | 应用灯效帧 |

### 完整灯效上传流程

根据固件命令分发器整理后的最小完整上传序列：

```text
5A A5 46 03 00 49    # 先关闭/清空
5A A5 46 03 01 4A
5A A5 41 02 43
5A A5 47 0D 00 <10-byte f0> <checksum>
5A A5 47 0D 01 <10-byte frame01> <checksum>
...
5A A5 47 0D 12 <10-byte frame18> <checksum>
5A A5 43 03 01 47
```

帧索引只发到 `0x12`（19 帧）。旧抓包里的 31 帧会写出缓冲区，
见「灯效缓冲区容量与 `0x47` 的帧数上限」一节。

旧抓包流程中的重复 `0x46 01`、带 payload 的第二次 `0x41`，以及两条
`0x45` 都不是完成上传所必需。当前实现逐条等待设备 ACK，因此也不再依赖固定延时。

智能温控灯效使用固件原生预设，不上传自定义帧（原因见「会写入数据闪存的命令」一节）。
固件无法自行读取电脑温度，因此主机监控循环会按当前 CPU/GPU 最高温度动态重发 `0x44`。
温度分区由用户配置：每段有一个下限温度和一个原生预设编号，回差也可调，
默认沿用历史行为——不高于 70°C 用预设 1，71–80°C 用预设 2，高于 80°C 用预设 3，回差 2°C。
向上进入某段需要温度达到该段下限加回差，向下退出需要低于本段下限减回差。
从自定义帧灯效切回智能温控时，必须先关闭输出并停止旧动画状态；`0x44`
会立即生成并应用原生动画，后面不能再发送自定义缓冲区提交命令 `0x43`。切换序列为：

```text
5A A5 44 03 00 47    # 停止/重置旧动画状态（不写闪存）
5A A5 46 03 01 4A    # 开启灯效；已经是开启状态时必须跳过，否则白白擦写一页闪存
5A A5 44 03 01 48    # 进入第一段的预设；后续由电脑温度动态更新
```

旧流程里开头那条 `46 00` 已经删除：它与紧随其后的 `46 01` 是同一个字段的两次落盘，
纯属多出两次闪存擦写。

`0x47` 的 `LEN=0D`，payload 为 `frame_index + 10 bytes`。

固件实际消费的上传头结构为：

```text
00 02 <first-keyframe> <last-keyframe> <transition-ticks> <brightness> <color-data...>
```

颜色区从偏移 `6` 开始，采用灯珠主序：`6 颗灯 × 10 个关键帧 × RGB`。
某一颜色的偏移为 `6 + led_index * 30 + keyframe_index * 3`。固件会再按头部
`brightness / 100` 缩放 RGB，所以主机端不能预先按亮度缩放，否则实际亮度会被平方。

速度常用编码：

| 速度 | 值 |
| --- | --- |
| fast | `0x05` |
| medium | `0x0A` |
| slow | `0x0F` |

已实现灯效模式：

| 模式 | 协议 / 数据特点 |
| --- | --- |
| 关闭 | `0x46 03 00` |
| 智能温控 | `44 00` 停旧动画后按需 `46 01` 开灯，再用 `0x44 01..05` 按温度分区切换动画（不写闪存） |
| 单色静态 | `last-keyframe=00`，6 颗灯写入同一颜色 |
| 多色静态 | `last-keyframe=00`，6 颗灯循环写入三种颜色 |
| 旋转 | `last-keyframe=05`，6 个关键帧在灯珠之间轮转自选颜色 |
| 流动 | `last-keyframe=05`，6 个关键帧轮转彩虹色 |
| 呼吸 | `last-keyframe=len(colors)*2-1`，彩色与黑色关键帧交替插值 |

### 亮度字段

固件没有独立的“亮度 0%/100%”命令。`0x43` 只负责提交，单独写某个 `0x47`
索引也只是修改缓冲区。自定义灯效亮度应写上传头偏移 `5` 的 `0..100`；RGB
颜色保留原值，由固件统一缩放。

## 查询、状态与内部命令

这些命令在固件中存在明确分支，但业务层未全部实测。建议把它们视为“可研究命令”，不要作为面向用户的稳定 API。

| CMD | 可能用途 | 说明 |
| --- | --- | --- |
| `0x01` | 设备/固件信息查询 | 固件构造固定回包并补校验 |
| `0x02` | 当前配置查询 | 返回一个 6 字节左右的配置摘要 |
| `0x04` / `0xF0` | 状态快照/配置刷新 | 构造固定状态帧 |
| `0x07` / `0x09` / `0x0B` | 状态查询 | 返回内部状态字段或固定信息块 |
| `0x24` | 退出实时模式 | 会清除实时转速模式标志 |
| `0x25` | 查询当前工作状态 | 返回当前挡位/模式相关字段 |
| `0x27` | 查询转速档案表 | 返回若干小端转速配置 |
| `0xED` / `0xEE` | 调试标志 A | 开关某内部状态标志 |
| `0xF1` / `0xF2` | 调试/校验标志 B | 会影响校验错误处理路径，不建议使用 |

| 字段 | 值 | 说明 |

## 生成命令的参考代码

```go
func buildFrame(cmd byte, payload ...byte) []byte {
    ln := byte(len(payload) + 2)
    frame := []byte{0x5A, 0xA5, cmd, ln}
    frame = append(frame, payload...)
    var sum byte
    for _, b := range frame[2:] {
        sum += b
    }
    frame = append(frame, sum)
    return frame
}

func buildRPM(rpm uint16) []byte {
    return buildFrame(0x21, byte(rpm), byte(rpm>>8))
}
```

## 建议的安全调用顺序

实时转速：

```text
5A A5 23 02 25
sleep 50ms
5A A5 21 04 <rpm_lo> <rpm_hi> <checksum>
```

RGB 灯效：

```text
46 03 00 -> 46 03 01 -> 45 02 -> 45 03 01 -> 41 02 -> 41 03 01
-> 47 0D 00/f0 -> 47 0D 01..1E/frame -> 43 03 01
```

配置项：

```text
0C 03 xx    # 通电自启动
0D 03 xx    # 智能启停
48 03 xx    # 挡位灯
```

## 会写入数据闪存的命令（重要）

以下结论来自 CH591 固件反编译（`firmware_reverse/analysis/decompiled/`），
直接决定主机端该怎么发命令。

固件里有两条落盘例程，都是「擦除一整页 256 字节数据闪存，再写回」：

| 例程 | 擦除地址 | 写入内容 |
| --- | --- | --- |
| `FUN_ram_00006194` | `0x1000` | 控制器状态 `0x14` 字节、运行结构 `0x18` 字节、LED 状态 `0x0c` 字节 |
| `FUN_ram_0000628e` | `0x2000` | 灯效帧缓冲区 |

调用它们的命令分支：

| 命令 | 是否落盘 | 是否先比较新旧值 |
| --- | --- | --- |
| `0x0C` 通电自启动 | 是 | **是**，值没变就不写 |
| `0x0D` 智能启停 | 是 | **是**，值没变就不写 |
| `0x46` 灯效开关 | 是 | **否**，每次调用都擦写 |
| `0x48` 挡位灯开关 | 是 | **否**，每次调用都擦写 |
| `0x43` 灯效提交 | 是（经事件 `0x20` 异步触发） | 否 |
| `0x44` 原生预设 | **否** | — |

`0x0C/0x0D` 有比较、`0x46/0x48` 没有，这个不对称说明厂商本意是要比较的，只是漏写了。
主机端必须自己补上：缓存设备侧的当前值，相同就不要下发。否则

* 每次应用自定义灯效 = 3 次闪存擦写（`0x46 00`、`0x46 01`、`0x43`）；
* 每次重连重放 = 4 次左右连续擦写（挡位灯 + 灯效开关 + 提交）。

连续的闪存擦写会长时间关中断，与 BLE/HID 链路和风扇测速中断争抢，是「散热器偶发重启」
最可能的主机侧成因；另外数据闪存的擦写寿命也有限。

两条落盘例程的开头都是：

```c
if (flash_state_byte == 9) { for (;;) { } }
```

一旦闪存状态字读到 9，固件会在命令处理函数里死循环——主机看到的是 ACK 超时，
随后升级为强制断连重连，重连又重放同一批命令。减少这些命令的下发次数是唯一的缓解手段。

因此：**智能温控灯效只使用 `0x44` 原生预设，不为温度分区上传自定义帧。**
温度分区是随负载持续切换的，用 `0x43` 实现等于把闪存擦写绑到温度曲线上。

## 固件不做边界检查的命令

`0x47` 的固件分支是：

```c
stream = get_stream_buffer_state();
copy_bytes_to_device_buffer(*stream + payload[0] * 10, payload + 1, 10);
```

帧索引 `payload[0]` 是一个完整字节，既不检查上界，也不检查缓冲区指针是否已分配
（只有 `0x41` 检查 `*stream == 0`）。发送 `0x47 FF ...` 会写到缓冲区之后 2550 字节处，
直接破坏固件内存。正常控制路径固定使用 `0x00..0x1E`，调试通道必须自行拦截越界索引。

`0x26` 的挡位索引虽然有 `0..3` 的检查，但它同时会清除实时模式标志并切换当前挡位，
主机在下发之后必须认为实时会话已经结束。

## 灯条与灯效引擎

设备端是一条连成一整条的灯带（带导光罩，相邻灯珠的光互相融合），共 **6 颗灯珠**。
固件帧缓冲区 `0x20004be0..0x20004bf2` 正好 18 字节，
移位输出函数按 **G、R、B** 顺序发送（WS2812 系列线序），缓冲区内部仍是 RGB。

上传缓冲区在 `0x200049c8`，布局与本文档 `0x47` 一节一致。固件 `FUN_ram_00007fa8`
把它重排成关键帧主序表（每关键帧 18 字节），随后：

* `FUN_ram_000080b2(k)` 装载关键帧 `k` 与 `k+1`（回环），装载时做 `value * brightness / 100`；
* `FUN_ram_00008180` 在两者之间线性插值，一次过渡共 `transitionTicks * 10` 个子步，
  走完切换到下一关键帧。

亮度只能由固件缩放这一次，主机不能预先按亮度缩放颜色。

`initialize_status_reporting` 把出厂默认灯效直接写进这个缓冲区，是可核对的实例：
`lastKeyframe=5`、`transitionTicks=10`、`brightness=70`，颜色表为

```text
palette = #0000FF #007F7F #00FF00 #7F7F00 #FF0000 #7F007F
LED i 的关键帧 k 取 palette[(i mod 3 + k) mod 6]
```

即一条以 3 颗灯为周期的六色旋转。应用内的灯条预览
（`frontend/src/app/lib/lightProgram.ts`）复刻的就是上面这套结构与插值算法。

## `0x44` 原生预设的真实内容

`0x44` 的分支是 `(**(code **)(rgb_controller_state + 0x10))(preset)`，调用 RGB 控制器
虚表的第 5 个槽位。这张虚表在已初始化数据段里，反编译产物看不到它的内容，但可以
从镜像本身解出来：

1. 启动代码 `reset_startup_initialize_memory_and_interrupts` 把 `.data` 从镜像
   `0x2abac` 拷到 RAM `0x20002128`；
2. `get_rgb_controller_state` 返回 `0x200025f0`，于是它在镜像里的位置是
   `0x2abac + (0x200025f0 - 0x20002128)` = `0x2b074`；
3. 读出该处的五个字：`0x83fa`、`0x8480`、`0x8090`、`0x7a14`、**`0x7ad0`**。
   最后一个就是 `0x44` 的处理函数——它在 curated 反编译产物里被漏掉了。

`0x7ad0` 的公共部分：亮度写死 100（所以智能温控模式下亮度滑块无效），
`firstKeyframe = 0`，`lastKeyframe` 先置 1；校验 `preset - 1 <= 4`（即合法值 1..5），
再经 `0x2a330` 的跳转表分派到五段生成代码，最后走 `0x8090` 让下一个渲染周期重启程序。

逐条模拟各段里的 `sb`/`sh`/`sw`，还原出的程序如下（亮度均为 100）：

| 预设 | lastKeyframe | transitionTicks | 效果 |
| ---: | ---: | ---: | --- |
| 1 | 3 | 10 | 绿色底 + 白色高光流动 |
| 2 | 3 | 6 | 黄色底 + 白色高光流动 |
| 3 | 3 | 2 | 红色底 + 白色高光流动 |
| 4 | 1 | 2 | 纯红常亮（两帧同色） |
| 5 | 2 | 10 | 红 → 粉三帧流动 |

1..3 是同一套排布，只换底色和速度。记底色为 A、过渡色 M、白色高光为 W：

```text
LED0  A M W M
LED1  M W M A
LED2  W M A M
LED3  A M W M      (生成循环跑两趟、每趟前进 3 颗灯，后三颗与前三颗相同)
LED4  M W M A
LED5  W M A M
```

| 预设 | A | M | W |
| ---: | --- | --- | --- |
| 1 | `#00FF00` | `#3FFF3F` | `#FFFFFF` |
| 2 | `#FFFF00` | `#FFFF3F` | `#FFFFFF` |
| 3 | `#FF0000` | `#FF3F3F` | `#FFFFFF` |

也就是说这三个预设是**流光**，不是闪烁或呼吸：一段白色高光以 3 颗灯为周期沿灯带
跑动。而 `transitionTicks` 依次是 10 / 6 / 2——温度越高的预设，流光跑得越快。

预设 5 有两张表，生成前调用 `0x755a` 读**运行配置字节**（即命令 `0x09` 返回、
命令 `0x0A` 写入的那个值）来选：

```text
运行配置 == 1        其它（含复位默认值 0）
LED0  #FF0000 #FF5F5F #FFB8B8      #FFFFFF #1E1EA0 #000050
LED1  #FFB8B8 #FF0000 #FF5F5F      #000050 #FFFFFF #1E1EA0
LED2  #FFB8B8 #FF5F5F #FF0000      #000050 #1E1EA0 #FFFFFF
LED3..5 与 LED0..2 相同
```

同一个字节还决定出厂默认灯效：等于 2 时 `initialize_status_reporting` 写的是
两帧同色的 `#B9FF00` 常亮，否则才是六色旋转。

应用内的智能温控预览（`frontend/src/app/lib/lightProgram.ts`）直接使用上面这些表，
和自定义灯效走完全相同的插值路径——因为设备端本来就是同一条路径。

## 控制器能力档位（`0x07`）会静默否决换挡

`0x07` 返回控制器能力档位。固件用它决定"这条挡位选择命令到底要不要真的换挡"，
而且 `0x08` 与 `0x26` 的规则并不相同：

| 命令 | 档位 1 | 档位 2 | 其它档位 |
| --- | --- | --- | --- |
| `0x08` 选择固定挡位 | 挡位 1..3 | 全部 | 全部 |
| `0x26` 写挡位转速并选中 | 挡位 1..2 | 挡位 1..3 | 全部 |

**两条分支都照常回 ACK=1。** `0x26` 无论如何都会把转速写进对应槽位，被否决的只是
"选中"这一步；`0x08` 被否决时连状态上报都不会发。所以主机不能只看 ACK 判断挡位是否
生效——要么先读 `0x07` 自己算上界，要么等 `0xEF` 状态上报确认实际挡位。

另外 `0x08` 的固件分支**完全不校验 payload**：任何字节都会被直接写进当前挡位字段，
主机必须自己限制在 `1..4`。

## 灯效缓冲区容量与 `0x47` 的帧数上限

流状态结构（RAM `0x20002604`）的第四个字是缓冲区容量，镜像里的初值是 `0x100`，
即 **256 字节**；缓冲区本体在 `0x200049c8`。分块写 `0x42` 会比较
`stream[1] + len <= stream[3]`，但 `0x47` 完全不检查。

固件真正会读回的只有 184 字节（`6 + 5*30 + 9*3 = 183` 是重排循环取到的最大偏移），
所以下发 **19 帧**（190 字节）就已经覆盖全部内容，且落在容量之内。按旧文档下发
31 帧是 310 字节，会越过缓冲区末尾 54 字节，写进紧随其后的关键帧渲染表
（`0x20004ac8`）——那块内存随后会被 `0x43` 重建，所以现象未必立刻可见，但这仍是一次
固件不设防的越界写，且白白多花 12 次命令往返。

## 未完全确认点

- GATT 可写特征 UUID 需要以实际设备枚举为准；抓包确认 handle `0x003c` 可写，通知侧常见 `FFF1`。
- `0x01`、`0x02`、`0x04`、`0x07`、`0x09`、`0x0B`、`0x25`、`0x27` 的回包字段还需要更多通知抓包来命名。
- `0xED`、`0xEE`、`0xF1`、`0xF2` 是固件内部/调试标志，不建议在正式控制流程中使用。
- 帧模板 `0xEF` 的 payload 共 9 字节，最后两字节（`payload[7:9]`）是一个另行 +1 的
  16 位量，含义未确认，当前实现只把它当原始十六进制展示。
